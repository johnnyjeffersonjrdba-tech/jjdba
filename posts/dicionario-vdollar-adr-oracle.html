Dicionário de dados, V$ e ADR no Oracle (1Z0-082 · Parte 4)

DBACERTIFICAÇÃO

Quarta parte do Guia 1Z0-082. Na Parte 3 vimos como ligar e desligar a instância. Agora o assunto é onde o DBA busca informação: o dicionário de dados (DBA_, ALL_, USER_, CDB_), as visões de performance dinâmica (V$) e o ADR, onde ficam o alert log, os trace files e os incidentes.

Cada afirmação técnica deste artigo foi conferida na documentação oficial do Oracle Database 19c. Os links estão em cada seção e reunidos no final.

1. O dicionário de dados

Using Data Dictionary Views

O dicionário de dados é o conjunto de tabelas e views somente leitura que guarda os metadados do banco: definição de cada objeto, usuários, privilégios, roles, espaço alocado, constraints e auditoria. O Oracle o consulta a cada SQL, para saber se o objeto existe e se você tem acesso, e o atualiza a cada DDL.

Ele tem duas camadas:

  • Base tables (OBJ$, TAB$, USER$…): guardam os dados de forma normalizada. Só o próprio Oracle deve ler e gravar nelas.
  • Views do dicionário (DBA_TABLES, ALL_USERS…): decodificam essas tabelas. É o que DBAs e desenvolvedores consultam.

O dono de tudo é o usuário SYS, e o dicionário fica na tablespace SYSTEM. Por isso ele só está disponível com o banco aberto. Para não ler o disco a cada parse, parte dele fica em memória no data dictionary cache, dentro da shared pool (Parte 1).

Para descobrir "qual view tem o que eu procuro", consulte a DICTIONARY (sinônimo DICT), que lista as views do dicionário com um comentário, e a DICT_COLUMNS, que descreve as colunas.

2. USER_, ALL_ e DBA_

Using Data Dictionary Views

A maior parte das views vem em trios, com as mesmas colunas e escopos diferentes:

Prefixo Mostra Quem pode consultar
USER_ Os objetos do seu schema Qualquer usuário
ALL_ Os objetos que você pode acessar (seus e os concedidos) Qualquer usuário
DBA_ Todos os objetos do banco SYSDBA, SELECT ANY DICTIONARY, SELECT_CATALOG_ROLE ou grant direto
  • As USER_ normalmente não têm a coluna OWNER: o dono é quem consulta.
  • ALL_ não quer dizer "todos os objetos do banco"; quer dizer os que você acessa.
  • Nem todo trio está completo: existe DBA_DATA_FILES, mas não USER_DATA_FILES.
  • Um usuário sem privilégio que consulta uma DBA_ recebe ORA-00942: table or view does not exist: para ele, é como se a view não existisse.
  • Os nomes ficam guardados em maiúsculas: WHERE table_name = 'EMP', e não 'emp'.

3. O dicionário num CDB: DBA_ × CDB_

Using Data Dictionary Views

Num CDB, a regra é:

  • DBA_ é local. No root mostra só o root; numa PDB, só aquela PDB.
  • CDB_ tem a coluna a mais CON_ID. Consultada do root, traz o root e as PDBs abertas; consultada de dentro de uma PDB, se comporta como a DBA_.
View No root Numa PDB
DBA_xxx Só o root Só a PDB
CDB_xxx Root + PDBs abertas, com CON_ID Só a PDB
V$xxx Todos os containers Só o container corrente

Exemplo prático, no root: SELECT con_id, COUNT(*) FROM cdb_users GROUP BY con_id; dá um retrato de todas as PDBs de uma vez.

4. Visões de performance dinâmica (V$)

Using Dynamic Performance Views

As V$ mostram o estado vivo da instância: sessões, processos, memória, parâmetros em vigor, SQL em execução, estado dos arquivos. Elas são atualizadas continuamente e seus contadores recomeçam a cada STARTUP.

De onde elas vêm:

  • X$: tabelas internas sobre memória e control file, não documentadas.
  • V_$: as views de verdade, de propriedade do SYS.
  • V$: sinônimos públicos das V_$. A documentação diz que DBAs e usuários devem consultar só as V$.

Três cuidados:

  • Não há leitura consistente. Como os dados mudam enquanto a consulta roda, a documentação recomenda só consultas simples. Para joins, sorts e GROUP BY pesados, copie os dados para uma tabela (CREATE TABLE ... AS SELECT) e analise a cópia.
  • Logo após a instalação, só SYS (ou SYSDBA) acessa as V$. Para liberar a outro usuário, use a role SELECT_CATALOG_ROLE.
  • GV$ é a mesma view com a coluna INST_ID: num RAC, traz os dados de todas as instâncias.

📖 Fontes: About Dynamic Performance Views · Data Dictionary and Dynamic Performance Views

5. O que responde em cada estágio — e quando usar DBA_ ou V$

Using Dynamic Performance Views

Estágio Responde
NOMOUNT V$ que leem da memória: V$INSTANCE, V$PARAMETER, V$SGA, V$DIAG_INFO
MOUNT + V$ que leem do control file: V$DATABASE, V$DATAFILE, V$LOG
OPEN + o dicionário (DBA_, ALL_, USER_, CDB_)

Para escolher entre DBA_ e V$, pense em "o que o banco é" × "o que a instância está fazendo":

  • DBA_ descreve a estrutura persistente: DBA_DATA_FILES, DBA_USERS, DBA_TABLESPACES.
  • V$ descreve o estado agora: V$SESSION, V$PARAMETER, V$DATAFILE.

Na prática: banco que não abre? Só as V$ ajudam. Relatório de capacidade? DBA_. Lentidão agora? V$.

6. ADR: o repositório de diagnóstico

Using the Automatic Diagnostic Repository (ADR)

O ADR é uma estrutura de diretórios fora do banco. Por isso ele continua disponível justamente quando o banco está fora do ar. Ali ficam o alert log, os trace files, os dumps de incidentes e os relatórios do Health Monitor.

  • A raiz é a ADR base, definida pelo parâmetro DIAGNOSTIC_DEST. O padrão vem do ORACLE_BASE; sem ele, usa $ORACLE_HOME/rdbms/log.
  • Desde o 11g, o DIAGNOSTIC_DEST substitui o BACKGROUND_DUMP_DEST e o USER_DUMP_DEST, que estão deprecated.
  • Cada instância tem o seu ADR home: diag/rdbms/<db_unique_name>/<SID>.
  • Não é preciso decorar o caminho: SELECT name, value FROM v$diag_info; mostra todos.

7. Alert log e trace files

Using the Alert Log and Trace Files

O alert log é o diário cronológico da instância. Ele registra STARTUP e SHUTDOWN, erros críticos, operações administrativas e parâmetros fora do padrão. É a primeira coisa que abro quando algo dá errado.

Ele existe em dois formatos:

  • log.xml, no subdiretório alert. É o oficial, e a Oracle recomenda usá-lo para qualquer análise automatizada.
  • alert_<SID>.log, em texto, no subdiretório trace, mantido por compatibilidade.

Os trace files são gravados por cada processo e também ficam em trace:

  • processo de background: <SID>_<processo>_<pid>.trc (ex.: cdbprd_lgwr_4321.trc);
  • server process: <SID>_ora_<pid>.trc.

Para achar o trace da sua sessão, consulte a linha Default Trace File da V$DIAG_INFO.

8. Problemas, incidentes e flood control

Using the Automatic Diagnostic Repository (ADR)

  • Problem: um erro crítico, como ORA-00600 (erro interno), ORA-07445 (exceção do SO) ou ORA-04031 (falta de memória na shared pool). Cada um tem uma problem key, por exemplo ORA 600 [4137].
  • Incident: cada ocorrência de um problem, com um ID numérico único no ADR. Um problem pode ter vários incidents.

O flood control evita que um erro repetido encha o disco de dumps. Os limites são fixos, por problem key:

Situação O que acontece
Mais de 5 incidentes em 1 hora ou 25 em 1 dia Os seguintes são registrados no alert log e no ADR, mas sem dumps
Mais de 50 em 1 hora ou 250 em 1 dia Os seguintes nem são registrados; só uma mensagem no alert log a cada 10 minutos

Para mandar ao Oracle Support, o IPS (Incident Packaging Service) junta sozinho tudo o que tem o número do incidente e gera um zip.

📖 Fonte: Diagnosing and Resolving Problems

9. ADRCI: a linha de comando do ADR

Using the Automatic Diagnostic Repository (ADR)

O ADRCI não pede usuário nem senha do banco: os dados do ADR são protegidos pelas permissões do sistema operacional. Por isso ele funciona com o banco parado.

  • Ao iniciar, o homepath é nulo, ou seja, todos os homes sob a ADR base são correntes.
  • Para trabalhar só com o banco, use SET HOMEPATH, com o caminho relativo à ADR base. Copie da saída de SHOW HOMES.
  • Alguns comandos, como os do IPS, não funcionam com vários homes correntes.
Comando Faz
SHOW HOMES Lista os ADR homes
SET HOMEPATH diag/rdbms/… Fixa um home
SHOW ALERT -TAIL Últimas 10 entradas do alert log
SHOW ALERT -TAIL -F Acompanha o alert log ao vivo
SHOW TRACEFILE -RT Traces, do mais recente para o mais antigo
SHOW PROBLEM / SHOW INCIDENT Problemas e incidentes
IPS PACK INCIDENT <id> IN /tmp Empacota um incidente em zip

📖 Fonte: ADRCI: ADR Command Interpreter

Laboratório: para você fazer no seu 19c

Conecte como sqlplus / as sysdba no CDB$ROOT. Troque dbprod pelo nome da sua PDB. Cada bloco tem um botão Copiar.

Passo 1 — USER_ × ALL_ × DBA_ como usuário comum. A consulta à DBA_ falha com ORA-00942.

-- conectado à PDB com um usuário comum de teste
SELECT COUNT(*) FROM user_tables;
SELECT COUNT(*) FROM all_tables;
SELECT COUNT(*) FROM dba_tables;

Passo 2 — O índice do dicionário.

SELECT table_name, comments FROM dict WHERE table_name LIKE 'DBA_DATA%';

Passo 3 — DBA_ × CDB_ no root.

SELECT COUNT(*) FROM dba_users;
SELECT con_id, COUNT(*) FROM cdb_users GROUP BY con_id ORDER BY con_id;
SELECT con_id, name, open_mode FROM v$containers ORDER BY con_id;

Passo 4 — V$ é sinônimo, V_$ é a view.

SELECT owner, object_name, object_type
FROM   dba_objects
WHERE  object_name IN ('V$SESSION', 'V_$SESSION');

Passo 5 — Onde está o ADR. Anote ADR Base, ADR Home, Diag Trace e Diag Alert.

SELECT name, value FROM v$diag_info;

Passo 6 — O alert log no shell. Use o caminho de Diag Trace do passo 5.

cd <Diag Trace>
tail -30 alert_*.log

Passo 7 — ADRCI. Nenhuma senha do banco é pedida.

adrci
show base
show homes
set homepath <copie o caminho rdbms de show homes>
show alert -tail 20
show problem
show incident
exit

Pontos de atenção que encontrei nos simulados

  • O dono do dicionário é SYS; a tablespace onde ele mora é que se chama SYSTEM.
  • O dicionário só está disponível com o banco aberto.
  • ALL_ mostra o que você acessa; "todos" é DBA_.
  • As USER_ normalmente não têm a coluna OWNER.
  • DBA_ no root não mostra as PDBs; para isso existe a CDB_.
  • V$ são sinônimos públicos; as views de verdade são as V_$.
  • As V$ não têm leitura consistente.
  • GV$ = V$ + INST_ID.
  • V$DATABASE precisa de MOUNT; o dicionário precisa de OPEN.
  • DIAGNOSTIC_DEST define a ADR base; o padrão vem do ORACLE_BASE.
  • O alert log em texto fica em trace/; o XML, em alert/.
  • Flood control: 5 por hora / 25 por dia sem dumps; 50 / 250 nem registra.
  • O ADRCI não pede login no banco, e o IPS exige um único home corrente.

Resumo em 5 linhas

  1. O dicionário é do SYS, fica na SYSTEM e só funciona com o banco aberto.
  2. USER_ ⊆ ALL_ ⊆ DBA_; num CDB, a CDB_ junta tudo com CON_ID.
  3. As V$ mostram a instância agora, sem leitura consistente, e zeram a cada STARTUP.
  4. O ADR fica fora do banco, em DIAGNOSTIC_DEST; a V$DIAG_INFO mostra os caminhos.
  5. O ADRCI lê o alert log e os incidentes sem login no banco; o IPS empacota para o Support.
