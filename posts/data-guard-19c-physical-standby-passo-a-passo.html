Data Guard 19c na prática: physical standby com RMAN DUPLICATE, ASM/OMF e Broker

DATAGUARDDBALINUX

Durante muito tempo, Data Guard foi para mim um assunto mais de estudo do que de rotina. Isso mudou quando passei a atuar numa célula de projetos de DBA. Ali tive a oportunidade de trabalhar em várias frentes e de participar da implantação de ambientes de Data Guard do início ao fim, com standby on-premises e na OCI.

Foi essa experiência que me motivou a escrever este artigo. Aqui está o passo a passo que uso para criar uma physical standby 19c com RMAN DUPLICATE FROM ACTIVE DATABASE, ASM com OMF e Data Guard Broker, pensado para treinar em laboratório. Cada etapa foi comparada com a documentação oficial da Oracle, e no caminho anotei os problemas que encontrei e como resolvi.

Cenário de laboratório, com nomes genéricos. Cada etapa foi conferida na documentação oficial do Oracle Database 19c; os links estão em cada seção e reunidos no final.

Antes de começar: Enterprise Edition × Standard Edition

Antes de planejar um Data Guard, confira a edição do banco. A documentação é direta:

"Oracle Data Guard is available only as a feature of Oracle Database Enterprise Edition. It is not available with Oracle Database Standard Edition."

Recurso Standard Edition 2 Enterprise Edition
Data Guard (Redo Apply, Broker, snapshot standby) Não Sim, incluído na licença EE
Active Data Guard (standby aberta READ ONLY com apply, far sync, cascata em tempo real) Não Só com a option Active Data Guard, licenciada à parte
Standby manual (cópia de archives + media recovery) Sim Sim

E no Standard Edition? A documentação diz que é possível simular um ambiente de standby:

  • os archived redo logs são copiados para o outro servidor com um utilitário do SO ou com scripts próprios, de tempos em tempos;
  • no destino, eles são registrados e aplicados com media recovery, mantendo a cópia do banco atualizada.

A própria Oracle avisa que essa configuração não oferece a facilidade de uso, o gerenciamento, a performance nem as capacidades de recuperação de desastre do Data Guard. Não há Broker, transporte automático nem switchover gerenciado.

A mesma página lembra outra regra: a mesma release do Enterprise Edition deve estar instalada no primário e nas standbys. A exceção são os upgrades rolling com standby lógica.

Tudo o que vem a seguir é Data Guard em Enterprise Edition, sem usar recursos do Active Data Guard.

Três regras de nomes que valem a pena fixar:

  • DB_NAME é igual nos dois lados: para criar uma standby com DUPLICATE, ele tem que ser o mesmo do primário.
  • DB_UNIQUE_NAME é diferente: é ele que identifica cada membro na configuração.
  • O ORACLE_SID pode ser igual, porque são servidores diferentes.

2. Preparar o primário

2.1 ARCHIVELOG, FORCE LOGGING e FLASHBACK

O primário precisa estar em ARCHIVELOG. Com FORCE LOGGING, nenhuma carga é feita sem gerar redo: a documentação explica que o modo padrão permite operações nologging, e esses dados ficariam faltando na standby.

srvctl stop database -db cdbprd
srvctl start database -db cdbprd -startoption mount

ALTER DATABASE ARCHIVELOG;
ALTER DATABASE FORCE LOGGING;
ALTER DATABASE FLASHBACK ON;

srvctl stop database -db cdbprd
srvctl start database -db cdbprd

SELECT log_mode, force_logging, flashback_on FROM v$database;

Esperado: ARCHIVELOG | YES | YES. O Flashback não é obrigatório para o Data Guard, mas é o que permite reinstate do antigo primário depois de um failover.

2.2 Standby Redo Logs (SRL)

Regra da documentação:

  • Quantidade: pelo menos um grupo a mais que os grupos de redo online, por thread.
  • Tamanho: cada SRL deve ser pelo menos do tamanho do maior redo online. A Oracle recomenda o mesmo tamanho para todos.
  • Onde: criar também no primário é boa prática, para quando ele assumir o papel de standby num switchover.

Exemplo para 3 grupos de 200 MB (thread 1) → 4 SRLs de 200 MB:

ALTER DATABASE ADD STANDBY LOGFILE THREAD 1 GROUP 101 ('+DATA') SIZE 200M;
ALTER DATABASE ADD STANDBY LOGFILE THREAD 1 GROUP 102 ('+DATA') SIZE 200M;
ALTER DATABASE ADD STANDBY LOGFILE THREAD 1 GROUP 103 ('+DATA') SIZE 200M;
ALTER DATABASE ADD STANDBY LOGFILE THREAD 1 GROUP 104 ('+DATA') SIZE 200M;

SELECT group#, thread#, bytes/1024/1024 AS mb, status FROM v$standby_log;

3. Password file

Sem SSL, cada standby precisa de uma cópia atualizada do password file do primário. É a causa número 1 de ORA-01017 e ORA-16191.

Com Grid e ASM, o password file costuma ficar dentro do ASM. Para copiar:

# primário (grid): extrai do ASM
asmcmd pwcopy +DATA/CDBPRD/PASSWORD/<arquivo> /tmp/orapwcdbprd

# standby (oracle): copia para o ORACLE_HOME e confere
scp oracle@srv-lab-ora-01:/tmp/orapwcdbprd $ORACLE_HOME/dbs/orapwcdbprd
md5sum $ORACLE_HOME/dbs/orapwcdbprd

O md5sum tem que ser igual ao do primário. Não recrie o arquivo com orapwd na standby.

A partir da 12.2, as alterações feitas depois no password file do primário são propagadas automaticamente para as standbys. A cópia inicial continua sendo manual.

4. Rede: listener estático e tnsnames

Durante o DUPLICATE, a standby está em NOMOUNT e não se registra no listener. Por isso, cada lado precisa de entradas estáticas no listener.ora do Grid. Elas também servem ao Broker, que exige um serviço registrado estaticamente para conseguir parar e subir as instâncias.

listener.ora (usuário grid) — standby srv-lab-ora-02. No primário é igual, com CDBPRD e CDBPRD_DGMGRL.

SID_LIST_LISTENER =
  (SID_LIST =
    (SID_DESC =
      (GLOBAL_DBNAME = CDBPRD_STBY)
      (ORACLE_HOME   = /u01/app/oracle/product/19c/dbhome_1)
      (SID_NAME      = cdbprd)
    )
    (SID_DESC =
      (GLOBAL_DBNAME = CDBPRD_STBY_DGMGRL)
      (ORACLE_HOME   = /u01/app/oracle/product/19c/dbhome_1)
      (SID_NAME      = cdbprd)
    )
  )
  • O ORACLE_HOME é o do banco, não o do Grid.
  • Depois de editar, rode lsnrctl reload. As entradas estáticas aparecem com status UNKNOWN, e isso é normal.

tnsnames.ora — idêntico nos dois servidores:

CDBPRD =
  (DESCRIPTION =
    (ADDRESS = (PROTOCOL = TCP)(HOST = srv-lab-ora-01)(PORT = 1521))
    (CONNECT_DATA = (SERVER = DEDICATED)(SERVICE_NAME = CDBPRD)))

CDBPRD_STBY =
  (DESCRIPTION =
    (ADDRESS = (PROTOCOL = TCP)(HOST = srv-lab-ora-02)(PORT = 1521))
    (CONNECT_DATA = (SERVER = DEDICATED)(SERVICE_NAME = CDBPRD_STBY)(UR = A)))

CDBPRD_DGMGRL =
  (DESCRIPTION =
    (ADDRESS = (PROTOCOL = TCP)(HOST = srv-lab-ora-01)(PORT = 1521))
    (CONNECT_DATA = (SERVER = DEDICATED)(SERVICE_NAME = CDBPRD_DGMGRL)))

CDBPRD_STBY_DGMGRL =
  (DESCRIPTION =
    (ADDRESS = (PROTOCOL = TCP)(HOST = srv-lab-ora-02)(PORT = 1521))
    (CONNECT_DATA = (SERVER = DEDICATED)(SERVICE_NAME = CDBPRD_STBY_DGMGRL)))

O (UR = A) permite conectar numa instância em NOMOUNT, que aparece como BLOCKED no listener.

5. Preparar a standby e testar a conexão

Para a instância auxiliar, a documentação pede um parameter file com DB_NAME. Como o banco é um CDB, inclua também ENABLE_PLUGGABLE_DATABASE=TRUE:

mkdir -p /u01/app/oracle/admin/cdbprd/adump
cat > $ORACLE_HOME/dbs/initcdbprd.ora <<'EOF'
DB_NAME=cdbprd
ENABLE_PLUGGABLE_DATABASE=TRUE
EOF

Se existir um spfilecdbprd.ora de uma tentativa anterior, renomeie-o: o Oracle lê o spfile antes do init.ora.

STARTUP NOMOUNT

Antes do DUPLICATE, teste a conexão nos dois servidores:

tnsping CDBPRD
tnsping CDBPRD_STBY
rman target sys@CDBPRD auxiliary sys@CDBPRD_STBY
Erro Causa provável
ORA-12154 Alias ausente no tnsnames.ora daquele servidor
ORA-12541 Listener parado, firewall ou nome de host errado
ORA-12514 / ORA-12528 Falta a entrada estática ou o lsnrctl reload; falta (UR = A)
ORA-01017 Password file diferente entre os lados ou senha errada

6. Parâmetros de Data Guard no primário

ALTER SYSTEM SET log_archive_config='DG_CONFIG=(cdbprd,cdbprd_stby)' SCOPE=BOTH;
ALTER SYSTEM SET log_archive_dest_1='LOCATION=USE_DB_RECOVERY_FILE_DEST VALID_FOR=(ALL_LOGFILES,ALL_ROLES) DB_UNIQUE_NAME=cdbprd' SCOPE=BOTH;
ALTER SYSTEM SET log_archive_dest_2='SERVICE=CDBPRD_STBY ASYNC VALID_FOR=(ONLINE_LOGFILES,PRIMARY_ROLE) DB_UNIQUE_NAME=cdbprd_stby' SCOPE=BOTH;
ALTER SYSTEM SET log_archive_dest_state_2=DEFER SCOPE=BOTH;
ALTER SYSTEM SET standby_file_management='AUTO' SCOPE=BOTH;
ALTER SYSTEM SET fal_server='CDBPRD_STBY' SCOPE=BOTH;
SHOW PARAMETER remote_login_passwordfile
Parâmetro Para que serve (documentação)
LOG_ARCHIVE_CONFIG DG_CONFIG precisa estar definido em cada banco da configuração
LOG_ARCHIVE_DEST_2 Envia o redo para a standby. ASYNC: o commit não espera o envio
STANDBY_FILE_MANAGEMENT=AUTO Datafiles criados ou removidos no primário são replicados na standby
FAL_SERVER De quem a standby busca os archives que faltarem (gap)
REMOTE_LOGIN_PASSWORDFILE EXCLUSIVE ou SHARED quando há password file

Deixo o DEST_2 em DEFER até a standby existir, para o alert log do primário não ficar registrando erro de envio.

7. Criar a standby com RMAN DUPLICATE (OMF)

Execute a partir da standby. Em outra janela, acompanhe o alert log dela.

rman target sys@CDBPRD auxiliary sys@CDBPRD_STBY

run {
  allocate channel p1 type disk;
  allocate channel p2 type disk;
  allocate auxiliary channel s1 type disk;
  duplicate target database for standby from active database dorecover nofilenamecheck
    spfile
      set db_unique_name='cdbprd_stby'
      set db_create_file_dest='+DATA'
      set db_create_online_log_dest_1='+DATA'
      set db_create_online_log_dest_2='+RECO'
      set db_recovery_file_dest='+RECO'
      set db_recovery_file_dest_size='20G'
      set control_files='+DATA','+RECO'
      set audit_file_dest='/u01/app/oracle/admin/cdbprd/adump'
      set log_archive_config='DG_CONFIG=(cdbprd,cdbprd_stby)'
      set log_archive_dest_1='LOCATION=USE_DB_RECOVERY_FILE_DEST VALID_FOR=(ALL_LOGFILES,ALL_ROLES) DB_UNIQUE_NAME=cdbprd_stby'
      set log_archive_dest_2='SERVICE=CDBPRD ASYNC VALID_FOR=(ONLINE_LOGFILES,PRIMARY_ROLE) DB_UNIQUE_NAME=cdbprd'
      set fal_server='CDBPRD'
      set standby_file_management='AUTO';
}

Dois detalhes:

  • Com OMF não é preciso DB_FILE_NAME_CONVERT nem LOG_FILE_NAME_CONVERT: o Oracle cria os arquivos em +DATA/CDBPRD_STBY/... sozinho.
  • NOFILENAMECHECK só deve ser usado duplicando para outro host. Num mesmo host, ele sobrescreveria os arquivos do banco de origem.

O DUPLICATE termina com Finished Duplicate Db e a standby fica em MOUNTED.

📖 Fonte: Duplicating Databases (RMAN)

8. Ligar o transporte e o apply

No primário, libere o envio:

ALTER SYSTEM SET log_archive_dest_state_2=ENABLE SCOPE=BOTH;
ALTER SYSTEM ARCHIVE LOG CURRENT;

Na standby (conectado no CDB$ROOT), inicie o Redo Apply em segundo plano. Desde a 12.1 esse comando já usa o real-time apply, aplicando o redo enquanto ele chega no standby redo log; a cláusula USING CURRENT LOGFILE está deprecated e não é mais necessária.

ALTER DATABASE RECOVER MANAGED STANDBY DATABASE DISCONNECT FROM SESSION;

Valide na standby com a V$DATAGUARD_PROCESS. A Oracle recomenda essa visão no lugar da V$MANAGED_STANDBY, que está descontinuada desde a 12.2.

SELECT role, thread#, sequence#, action FROM v$dataguard_process;

SELECT name, value FROM v$dataguard_stats
WHERE  name IN ('transport lag', 'apply lag');

SELECT * FROM v$archive_gap;
  • recovery logmerger com APPLYING_LOG indica que o redo está sendo aplicado.
  • v$archive_gap deve voltar vazia.

Ligue também o Flashback na standby. A Oracle recomenda o Flashback Database em todos os bancos da configuração: sem ele, um banco desabilitado depois de um failover não pode ser reinstaurado (REINSTATE) e precisa ser recriado.

ALTER DATABASE RECOVER MANAGED STANDBY DATABASE CANCEL;
ALTER DATABASE FLASHBACK ON;
ALTER DATABASE RECOVER MANAGED STANDBY DATABASE DISCONNECT FROM SESSION;

📖 Fontes: Creating a Physical Standby Database · Switchovers and Failovers (Broker) · Managing Physical Standby Databases

9. Data Guard num CDB: e a PDB dbprod?

Num ambiente multitenant, a documentação deixa claro:

  • O papel é do CDB inteiro. As PDBs não têm papel próprio: um switchover ou failover troca o papel do CDB com todas as PDBs.
  • RECOVER MANAGED STANDBY só funciona no root. Não é permitido dentro de uma PDB.
  • Com STANDBY_FILE_MANAGEMENT=AUTO, datafiles e PDBs novas criadas no primário são criadas na standby automaticamente.

Para conferir a PDB na standby, conectado no root:

SHOW PDBS
SELECT con_id, name, open_mode FROM v$pdbs;

A DBPROD aparece MOUNTED, como o resto da standby. Abri-la em READ ONLY com o apply ligado é o recurso Active Data Guard, que exige licença própria.

📖 Fontes: Creating a Physical Standby Database · Redo Apply Services

10. Registrar a standby no Grid (Oracle Restart)

Sem esse registro, a standby não sobe sozinha depois de um reboot do servidor.

srvctl add database -db cdbprd_stby -dbname cdbprd -instance cdbprd \
  -oraclehome /u01/app/oracle/product/19c/dbhome_1 \
  -spfile /u01/app/oracle/product/19c/dbhome_1/dbs/spfilecdbprd.ora \
  -pwfile /u01/app/oracle/product/19c/dbhome_1/dbs/orapwcdbprd \
  -role PHYSICAL_STANDBY -startoption MOUNT -stopoption IMMEDIATE \
  -diskgroup "DATA,RECO"

srvctl stop database -db cdbprd_stby
srvctl start database -db cdbprd_stby

11. Data Guard Broker

11.1 Limpar o destino de redo remoto

Antes de adicionar a standby à configuração, a documentação exige limpar o LOG_ARCHIVE_DEST_n remoto da standby; caso contrário dá ORA-16698. No primário ela diz que o destino pode ficar como está, mas eu prefiro limpar nos dois, para o Broker assumir o transporte sozinho:

ALTER SYSTEM SET log_archive_dest_2='' SCOPE=BOTH;

11.2 Arquivos do Broker e start (nos dois)

O Broker exige spfile. Os arquivos de configuração só podem ser alterados com o Broker parado, então defina-os antes do DG_BROKER_START:

-- primário
ALTER SYSTEM SET dg_broker_config_file1='+DATA/CDBPRD/dr1cdbprd.dat' SCOPE=BOTH;
ALTER SYSTEM SET dg_broker_config_file2='+RECO/CDBPRD/dr2cdbprd.dat'  SCOPE=BOTH;
ALTER SYSTEM SET dg_broker_start=TRUE SCOPE=BOTH;

-- standby
ALTER SYSTEM SET dg_broker_config_file1='+DATA/CDBPRD_STBY/dr1cdbprd_stby.dat' SCOPE=BOTH;
ALTER SYSTEM SET dg_broker_config_file2='+RECO/CDBPRD_STBY/dr2cdbprd_stby.dat'  SCOPE=BOTH;
ALTER SYSTEM SET dg_broker_start=TRUE SCOPE=BOTH;

11.3 Criar e habilitar a configuração (no primário)

dgmgrl sys@CDBPRD_DGMGRL

CREATE CONFIGURATION 'DG_CDBPRD' AS
  PRIMARY DATABASE IS 'cdbprd'
  CONNECT IDENTIFIER IS 'CDBPRD_DGMGRL';

ADD DATABASE 'cdbprd_stby' AS
  CONNECT IDENTIFIER IS 'CDBPRD_STBY_DGMGRL'
  MAINTAINED AS PHYSICAL;

EDIT DATABASE 'cdbprd' SET PROPERTY StaticConnectIdentifier =
  '(DESCRIPTION=(ADDRESS=(PROTOCOL=TCP)(HOST=srv-lab-ora-01)(PORT=1521))(CONNECT_DATA=(SERVICE_NAME=CDBPRD_DGMGRL)(INSTANCE_NAME=cdbprd)(SERVER=DEDICATED)))';

EDIT DATABASE 'cdbprd_stby' SET PROPERTY StaticConnectIdentifier =
  '(DESCRIPTION=(ADDRESS=(PROTOCOL=TCP)(HOST=srv-lab-ora-02)(PORT=1521))(CONNECT_DATA=(SERVICE_NAME=CDBPRD_STBY_DGMGRL)(INSTANCE_NAME=cdbprd)(SERVER=DEDICATED)))';

ENABLE CONFIGURATION;

O StaticConnectIdentifier é o endereço que o Broker usa para subir e derrubar as instâncias, por exemplo num switchover. Ele precisa apontar para um serviço registrado estaticamente.

11.4 Validar

SHOW CONFIGURATION;
SHOW CONFIGURATION LAG;
VALIDATE DATABASE 'cdbprd_stby';
VALIDATE NETWORK CONFIGURATION FOR ALL;

O esperado é Configuration Status: SUCCESS e Ready for Switchover: Yes.

12. Script de verificação da standby

Uso este script no dia a dia para checar a saúde da standby em uma só execução: papel, processos, lag, recebido × aplicado, gap, SRLs, erros recentes e uso da FRA.

SET LINES 200 PAGES 100
-- 1. Banco
SELECT name, db_unique_name, database_role, open_mode, protection_mode,
       switchover_status, flashback_on, force_logging
FROM   v$database;

-- 2. Processos (apply e recebimento)
SELECT name, role, action, thread#, sequence#
FROM   v$dataguard_process
WHERE  role LIKE 'RFS%' OR name LIKE 'MRP%' OR role LIKE 'recovery%'
ORDER  BY role, thread#;

-- 3. Lag
SELECT name, value, time_computed
FROM   v$dataguard_stats
WHERE  name IN ('transport lag', 'apply lag', 'apply finish time');

-- 4. Recebido x aplicado
SELECT thread#, MAX(sequence#) AS recebido,
       MAX(CASE WHEN applied = 'YES' THEN sequence# END) AS aplicado
FROM   v$archived_log
WHERE  resetlogs_change# = (SELECT resetlogs_change# FROM v$database)
GROUP  BY thread#;

-- 5. Gap (esperado: nenhuma linha)
SELECT thread#, low_sequence#, high_sequence# FROM v$archive_gap;

-- 6. Standby redo logs
SELECT group#, thread#, sequence#, bytes/1024/1024 AS mb, status FROM v$standby_log;

-- 7. Erros recentes do Data Guard
SELECT timestamp, facility, severity, message
FROM   v$dataguard_status
WHERE  severity IN ('Error', 'Fatal')
ORDER  BY timestamp DESC
FETCH  FIRST 10 ROWS ONLY;

-- 8. Uso da FRA
SELECT name, ROUND(space_used/space_limit*100, 1) AS pct_usado FROM v$recovery_file_dest;

13. Troubleshooting

Erro / sintoma Correção
ORA-01017 / ORA-16191 Recopiar o password file do primário e conferir o md5sum
ORA-01017 mesmo no primário via TNS SID_NAME com a caixa errada no listener.ora (no Linux o SID diferencia maiúsculas)
ORA-12514 / ORA-12528 Entrada estática + lsnrctl reload; (UR = A) no tnsnames
ORA-09925 Criar o diretório adump na standby
ORA-16057 DB_UNIQUE_NAME da standby ausente no DG_CONFIG do primário
ORA-01153 O apply já está rodando: CANCEL e iniciar de novo
ORA-16698 LOG_ARCHIVE_DEST_n remoto ainda definido na standby: limpar antes de adicionar no Broker
Standby não sobe após reboot Registrar no Oracle Restart (srvctl add database)

Lições aprendidas

  • O SID diferencia maiúsculas no Linux. Uma instância cdbprd com SID_NAME = CDBPRD no listener aponta para uma instância que não existe e gera ORA-01017.
  • Mantenha a mesma versão (RU) nos dois lados. A documentação exige a mesma release do Enterprise Edition no primário e nas standbys; RUs diferentes só se justificam temporariamente, durante um standby-first patching.
  • Password file: sempre copie do primário e compare o md5sum.
  • Valide a conectividade nos dois sentidos antes do DUPLICATE. Isso economiza horas de troubleshooting.
  • DEST_2 em DEFER até a standby existir mantém o alert log limpo.
  • OMF simplifica: sem *_FILE_NAME_CONVERT, os arquivos vão para o diskgroup certo sozinhos.
