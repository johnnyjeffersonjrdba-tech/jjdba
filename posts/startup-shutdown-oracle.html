STARTUP e SHUTDOWN no Oracle: estágios, modos e PDBs (1Z0-082 · Parte 3)

DBACERTIFICAÇÃO

Terceira parte do Guia 1Z0-082. Nas partes 1 e 2 vimos o que é a instância e onde os dados ficam. Agora o assunto é ligar e desligar o banco: o que acontece em cada estágio do STARTUP, a diferença real entre os quatro modos de SHUTDOWN e como isso funciona num CDB com PDBs.

Cada afirmação técnica deste artigo foi conferida na documentação oficial do Oracle Database 19c. Os links estão em cada seção e reunidos no final.

1. Os três estágios do STARTUP

Starting Up Oracle Database Instances

Subir um banco não é um evento único: são três estágios em sequência, e cada um abre uma camada a mais.

Estágio O que lê / abre V$INSTANCE.STATUS Uso típico
NOMOUNT Parameter file (spfile ou pfile); aloca a SGA, sobe os processos, abre o alert log STARTED Criar o banco, recriar o control file
MOUNT Control files → descobre datafiles e redo logs, sem abri-los MOUNTED Ligar/desligar ARCHIVELOG, recovery completo do banco
OPEN Datafiles e online redo logs; faz instance recovery se preciso OPEN Operação normal
  • STARTUP sem opção é o mesmo que STARTUP OPEN: faz os três estágios de uma vez.
  • O SQL*Plus conta a história nas mensagens: ORACLE instance started. → Database mounted. → Database opened.

Um detalhe importante: a instância monta, abre e fecha o banco uma única vez. Depois de fechado, é preciso uma nova instância (SHUTDOWN + STARTUP) para abrir de novo.

📖 Fontes: Oracle Database Instance · Starting Up and Shutting Down · V$INSTANCE

2. O que responde em cada estágio

Starting Up Oracle Database Instances

A regra da documentação é simples:

  • Instância iniciada (NOMOUNT): funcionam as visões V$ que leem da memória, como V$INSTANCE, V$SGA e V$PARAMETER.
  • Banco montado (MOUNT): passam a funcionar as que leem do disco, como V$DATABASE e V$DATAFILE, que vêm do control file.
  • Banco aberto (OPEN): só aqui funciona o dicionário de dados (DBA_, ALL_, USER_), porque ele fica na tablespace SYSTEM, dentro de um datafile.

Na prática, consultar V$DATABASE em NOMOUNT dá database not mounted, e consultar DBA_TABLESPACES em MOUNT dá database not open.

3. As opções do STARTUP

Starting Up Oracle Database Instances

Comando O que faz
STARTUP Sobe até OPEN (READ WRITE)
STARTUP NOMOUNT Para em NOMOUNT. Não combina com MOUNT nem OPEN
STARTUP MOUNT Para em MOUNT; depois, ALTER DATABASE OPEN
STARTUP OPEN READ ONLY Abre só para leitura
STARTUP RESTRICT Só entra quem tem o privilégio RESTRICTED SESSION
STARTUP FORCE Se a instância está no ar, faz SHUTDOWN ABORT e sobe de novo
STARTUP PFILE=arquivo Usa um parameter file texto do cliente

Sobre o PFILE: sem essa opção, o servidor procura primeiro o spfile padrão e, se não achar, o pfile padrão.

Sobre o FORCE: a documentação o recomenda só em situações anormais, quando os outros modos de shutdown não funcionam ou a instância tem problema para subir. No alert log aparece Shutting down instance (abort) seguido de Starting ORACLE instance (normal).

Com a instância no ar, avança-se de estágio com ALTER DATABASE MOUNT e ALTER DATABASE OPEN.

4. Os quatro modos de SHUTDOWN

Shutting Down Oracle Database Instances

O ponto de partida: nenhum modo aceita novas conexões, nem o NORMAL. O que muda é quanto o Oracle espera e se ele fecha tudo de forma consistente.

Modo Espera usuários saírem Espera transações Transações ativas Instance recovery depois
NORMAL (padrão) Sim Sim Os próprios usuários encerram Não
TRANSACTIONAL Não Sim Terminam; depois os clientes são desconectados Não
IMMEDIATE Não Não Rollback automático Não
ABORT Não Não Sem rollback Sim (automática)

O que cada um significa na prática:

  • NORMAL: espera todo mundo se desconectar sozinho. Uma sessão esquecida aberta segura o shutdown.
  • TRANSACTIONAL: não deixa iniciar transação nova e espera só as que estão em andamento; quem estiver ocioso é desconectado.
  • IMMEDIATE: interrompe o SQL em execução, desconecta os usuários e faz rollback. "Imediato" não quer dizer instantâneo: o rollback de uma transação grande pode demorar.
  • ABORT: termina tudo na hora, sem rollback e sem fechar os arquivos de forma ordenada. O próximo STARTUP faz instance recovery automaticamente. As transações confirmadas não se perdem, porque o redo delas já está no online redo log (Parte 2).

Timeout: se o que bloqueia o shutdown não acontece em uma hora, o comando é cancelado com ORA-01013. A documentação manda considerar a instância num estado imprevisível, reenviar o SHUTDOWN e, se continuar falhando, usar SHUTDOWN ABORT.

📖 Fontes: Starting Up and Shutting Down · SQL*Plus — SHUTDOWN · Oracle Database Instance

5. SHUTDOWN por dentro: o STARTUP ao contrário

Shutting Down Oracle Database Instances

Nos modos NORMAL, TRANSACTIONAL e IMMEDIATE, o fechamento é consistente e segue três etapas:

  1. Database closed. — grava o conteúdo da SGA e fecha os datafiles e os online redo logs. Os control files continuam abertos.
  2. Database dismounted. — desassocia o banco e fecha os control files.
  3. ORACLE instance shut down. — libera a SGA e encerra os processos.

No ABORT aparece só a última linha.

Depois do shutdown, a sessão continua conectada, mas a uma instância ociosa (idle instance). É a partir dela que se faz o próximo STARTUP.

📖 Fontes: Oracle Database Instance · Starting Up and Shutting Down

6. Modo restrito e quiesce

Starting Up Oracle Database Instances

Modo restrito mantém o banco aberto, mas só para quem tem o privilégio RESTRICTED SESSION. É usado em manutenção e cargas de dados.

  • Na subida: STARTUP RESTRICT. Com o banco no ar: ALTER SYSTEM ENABLE RESTRICTED SESSION.
  • Para sair: ALTER SYSTEM DISABLE RESTRICTED SESSION, sem precisar reiniciar.
  • Quem já está conectado não é derrubado. A documentação sugere encerrar essas sessões antes da manutenção.
  • Com a instância restrita, nem o administrador acessa remotamente pelo listener: só localmente, no servidor.

Quiesce (ALTER SYSTEM QUIESCE RESTRICTED) deixa trabalhar só os DBAs, e aqui DBA quer dizer apenas SYS e SYSTEM. Quem tem a role DBA não basta. Para voltar ao normal: ALTER SYSTEM UNQUIESCE.

📖 Fonte: Starting Up and Shutting Down

7. STARTUP e SHUTDOWN num CDB

Starting Up Oracle Database Instances

Num CDB, o startup é feito no root por um usuário comum (na prática, sqlplus / as sysdba). A documentação é clara: quando o CDB abre, o root abre e os outros containers ficam montados.

Para abrir as PDBs, use ALTER PLUGGABLE DATABASE:

ALTER PLUGGABLE DATABASE pdb1 OPEN;
ALTER PLUGGABLE DATABASE ALL OPEN;
ALTER PLUGGABLE DATABASE ALL EXCEPT pdb2 CLOSE IMMEDIATE;

SAVE STATE faz a PDB voltar no mesmo modo depois de um restart do CDB: se estava READ WRITE, volta READ WRITE; se estava montada, volta montada. DISCARD STATE desfaz isso, e a PDB passa a voltar sempre montada. Os estados salvos aparecem em DBA_PDB_SAVED_STATES.

Mais três detalhes:

  • Dentro da PDB, o SHUTDOWN fecha a PDB, e o STARTUP a abre.
  • OPEN RESTRICTED FORCE numa PDB aberta encerra as sessões sem RESTRICTED SESSION, com rollback das transações delas.
  • Com o CDB em ARCHIVELOG, CLOSE ABORT fecha a PDB à força, sem checkpoint dos datafiles.

8. Quem pode ligar e desligar o banco

Starting Up Oracle Database Instances

Com o banco fechado, o dicionário não está disponível para conferir senhas. Por isso STARTUP e SHUTDOWN exigem um privilégio administrativo autenticado fora do banco: SYSDBA, SYSOPER, SYSBACKUP ou SYSDG.

SYSDBA SYSOPER
STARTUP / SHUTDOWN Sim Sim
ALTER DATABASE OPEN / MOUNT / BACKUP, ARCHIVELOG Sim Sim
Recovery Completa e incompleta Só completa
CREATE / DROP DATABASE Sim Não
Ver dados de usuários Sim Não
Schema ao conectar SYS PUBLIC

Como esses usuários se autenticam:

  • Pelo sistema operacional: o usuário do SO está no grupo do Oracle e conecta com / as sysdba.
  • Pelo password file: necessário para conexões administrativas em rede não segura.
  • Se você atende aos requisitos dos dois, a autenticação pelo SO tem precedência.

Mais uma regra: não dá para fazer STARTUP nem SHUTDOWN conectado por shared server. A conexão precisa ser dedicada.

Laboratório: para você fazer no seu 19c

⚠️ Só em laboratório. Os passos abaixo derrubam e reiniciam a instância. Nunca rode em produção.

Conecte como sqlplus / as sysdba no CDB$ROOT. Troque orclpdb1 pelo nome da sua PDB.

Passo 1 — Retrato antes de mexer. Anote o STARTUP_TIME.

SELECT instance_name, status, logins,
       TO_CHAR(startup_time, 'DD/MM HH24:MI:SS') AS subiu
FROM   v$instance;
SHOW PDBS

Passo 2 — Desligar de forma consistente. Observe as três mensagens.

SHUTDOWN IMMEDIATE

Passo 3 — Só a instância (NOMOUNT). V$DATABASE ainda não responde; o STARTUP_TIME mudou.

STARTUP NOMOUNT
SELECT status, TO_CHAR(startup_time, 'DD/MM HH24:MI:SS') AS subiu FROM v$instance;
SHOW PARAMETER control_files
SELECT name FROM v$database;

Passo 4 — Montar (MOUNT). V$DATABASE e V$DATAFILE respondem; DBA_TABLESPACES ainda não.

ALTER DATABASE MOUNT;
SELECT status FROM v$instance;
SELECT name, open_mode FROM v$database;
SELECT COUNT(*) FROM dba_tablespaces;

Passo 5 — Abrir e ver as PDBs. A sua PDB aparece MOUNTED até você abri-la.

ALTER DATABASE OPEN;
SHOW PDBS
ALTER PLUGGABLE DATABASE ALL OPEN;
ALTER PLUGGABLE DATABASE orclpdb1 SAVE STATE;
SELECT con_name, state FROM dba_pdb_saved_states;

Passo 6 — Modo restrito sem reiniciar.

ALTER SYSTEM ENABLE RESTRICTED SESSION;
SELECT logins FROM v$instance;
ALTER SYSTEM DISABLE RESTRICTED SESSION;
SELECT logins FROM v$instance;

Passo 7 — ABORT e a instance recovery automática. Depois, procure no alert log as mensagens de crash recovery.

SHUTDOWN ABORT
STARTUP

Passo 8 — SHUTDOWN dentro da PDB. A PDB fecha, mas a instância continua OPEN.

ALTER SESSION SET CONTAINER = orclpdb1;
SHUTDOWN IMMEDIATE
SELECT name, open_mode FROM v$pdbs;
SELECT status FROM v$instance;
STARTUP
ALTER SESSION SET CONTAINER = cdb$root;

Pontos de atenção que encontrei nos simulados

  • NOMOUNT lê o parameter file; o control file só é aberto em MOUNT.
  • STARTUP sem opção = STARTUP OPEN. SHUTDOWN sem opção = SHUTDOWN NORMAL.
  • STARTUP FORCE = SHUTDOWN ABORT + STARTUP.
  • ARCHIVELOG se liga com o banco montado, não aberto.
  • Views DBA_ só funcionam com o banco aberto.
  • Nenhum modo de shutdown aceita novas conexões.
  • TRANSACTIONAL espera transações, não usuários ociosos.
  • Só o ABORT exige instance recovery no próximo startup, e ela é automática.
  • Timeout de 1 hora: só para quem espera (NORMAL e TRANSACTIONAL).
  • ENABLE RESTRICTED SESSION não derruba quem já está conectado.
  • No quiesce, "DBA" é só SYS e SYSTEM.
  • Depois do STARTUP do CDB, as PDBs ficam montadas, a menos que tenham estado salvo.
  • A role DBA não basta para STARTUP e SHUTDOWN; é preciso SYSDBA ou SYSOPER (ou SYSBACKUP/SYSDG).
  • SYSOPER entra como PUBLIC e não faz CREATE DATABASE nem recovery incompleta.

Resumo em 5 linhas

  1. STARTUP: NOMOUNT (parameter file) → MOUNT (control files) → OPEN (datafiles e redo).
  2. SHUTDOWN faz o caminho inverso: fecha, desmonta e encerra a instância.
  3. NORMAL espera usuários, TRANSACTIONAL espera transações, IMMEDIATE faz rollback e ABORT deixa a recovery para o próximo startup.
  4. Num CDB, o root abre e as PDBs ficam montadas; SAVE STATE guarda o modo delas para o próximo restart.
  5. Só SYSDBA/SYSOPER (e afins) ligam e desligam o banco, porque o dicionário não está disponível com ele fechado.
