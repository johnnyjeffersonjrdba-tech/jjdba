1. Instância × banco de dados

Understanding Oracle Database Instance Configurations

No dia a dia a gente fala "o banco" para tudo, mas a Oracle separa duas coisas bem diferentes:

👉 Instância: o que está vivo na memória. É a SGA mais os processos de background.

👉 Banco de dados: o conjunto de arquivos em disco. São os datafiles, tempfiles, control files e online redo log files.

Como uma vive na memória e o outro no disco, dá para ter a instância sem banco (no estágio NOMOUNT) e o banco sem instância (tudo desligado, os arquivos continuam lá).

Instância Banco de dados
O que é SGA + processos de background Datafiles, tempfiles, control files, online redo logs
Onde vive Memória do servidor Disco (sistema de arquivos ou ASM)
Como identifico INSTANCE_NAME (o SID) DB_NAME e DBID
Onde consulto V$INSTANCE V$DATABASE

Cardinalidade entre instância e banco:

  • Single-instance: relação 1:1 entre banco e instância.
  • RAC: relação 1:N, ou seja, várias instâncias abrem o mesmo banco.
  • Em qualquer configuração: uma instância se associa a um único banco por vez.

O que acontece no STARTUP:

  1. NOMOUNT: procura o spfile (e, se não achar, o pfile), aloca a SGA, sobe os processos de background e abre o alert log. Ainda não há banco associado.
  2. MOUNT: lê o control file e passa a saber onde estão os arquivos do banco.
  3. OPEN: abre os datafiles e os online redo logs. A partir daqui o usuário entra.

Um detalhe importante: a instância só monta, abre e fecha o banco uma vez. Depois que o banco é fechado, é preciso iniciar uma nova instância (SHUTDOWN + STARTUP) para abri-lo de novo.

2. Multitenant: CDB e PDB

Understanding Oracle Database Instance Configurations

No 19c, o normal é trabalhar com CDB (container database). Um CDB tem:

  • exatamente um CDB$ROOT;
  • exatamente uma PDB$SEED, o modelo usado para criar novas PDBs (não dá para criar nem alterar objetos nela);
  • zero ou mais PDBs, que são os bancos "de verdade" das aplicações.

O ponto principal: todas as PDBs dividem a mesma instância, ou seja, a mesma SGA e os mesmos processos de background. O CDB tem um control file e um online redo log. Cada PDB tem as suas próprias tablespaces SYSTEM e SYSAUX e o seu próprio dicionário de dados. A undo depende do modo:

  • Local undo: cada PDB tem a sua tablespace de undo.
  • Shared undo: existe uma só undo ativa para o CDB inteiro.

CON_ID, que aparece em todas as visões V$:

CON_ID Significa
0 O CDB inteiro (ou um non-CDB)
1 CDB$ROOT
2 PDB$SEED
3 em diante PDBs criadas pelo usuário, application roots e application seeds

Usuários:

  • O comum é criado no root e precisa começar com o prefixo do COMMON_USER_PREFIX (por padrão, C##).
  • O local existe só dentro da sua PDB e não pode começar com C##.

3. SGA: a memória compartilhada

Understanding Oracle Database Memory and Process Structures

A SGA é a memória compartilhada por todos os processos da instância. Ela é dividida assim:

Componente O que guarda Atenção
Database buffer cache Cópias dos blocos de dados lidos dos datafiles Detalhes na seção 4
Redo log buffer Redo entries (a descrição de cada mudança) Quem grava em disco é o LGWR
Shared pool Library cache, data dictionary cache e server result cache O result cache fica dentro da shared pool
Large pool UGA em shared server, buffers de parallel execution e do RMAN Opcional e sem lista LRU
Java pool / Streams pool Código e dados Java de sessão na JVM / GoldenGate, XStream, Advanced Queuing e Data Pump
Fixed SGA Área interna de controle O tamanho é definido pelo Oracle e não pode ser alterado
In-Memory Area IM column store Opcional; exige a opção Database In-Memory

A library cache guarda o plano de execução de cada SQL:

  • Se o SQL já está lá, é um soft parse (reaproveita o que existe).
  • Se não está, é um hard parse, caro em CPU.

Na prática, é por isso que se insiste tanto em bind variables.

📖 Fontes: Memory Architecture · STREAMS_POOL_SIZE

4. Buffer cache por dentro

Understanding Oracle Database Memory and Process Structures

Cada buffer está em um destes estados:

  • unused: disponível, nunca foi usado ou está livre;
  • clean: já foi usado, mas não precisa ser gravado antes de ser reaproveitado;
  • dirty: foi alterado e ainda não foi gravado em disco.

E existe o pinned, que é outra coisa: o buffer fica "preso" enquanto uma sessão o acessa, para não sair da memória naquele instante.

O buffer cache pode ter pools extras:

  • KEEP: para blocos muito acessados que eu quero manter em memória.
  • RECYCLE: para blocos pouco usados, que não devem expulsar os outros.

📖 Fonte: Memory Architecture

5. PGA e UGA

Understanding Oracle Database Memory and Process Structures

A diferença entre SGA e PGA, de forma direta:

👉 A PGA é a memória privada de cada processo e nunca fica na SGA. É nela que ficam a private SQL area e as work areas, que é onde rodam o sort de um ORDER BY e o hash join. Se os dados não cabem na work area, o Oracle usa o disco temporário. Fica mais lento, mas não dá erro.

👉 A UGA é a memória da sessão. Onde ela fica depende do tipo de conexão:

  • Dedicated server: dentro da PGA.
  • Shared server: dentro da SGA, porque qualquer shared server pode atender a próxima chamada da sessão.

Outro ponto que confunde: o PGA_AGGREGATE_TARGET é um alvo, e o consumo pode passar dele. O limite rígido é o PGA_AGGREGATE_LIMIT.

📖 Fontes: Memory Architecture · PGA_AGGREGATE_TARGET · PGA_AGGREGATE_LIMIT

6. AMM × ASMM × manual

Understanding Oracle Database Memory and Process Structures

São três formas de dizer ao Oracle quanta memória usar:

AMM ASMM
Parâmetro MEMORY_TARGET: SGA + PGA SGA_TARGET: só a SGA
O Oracle distribui Entre SGA e PGA Entre os pools da SGA
Teto MEMORY_MAX_TARGET SGA_MAX_SIZE
Sempre manual LOG_BUFFER, KEEP, RECYCLE, caches de bloco não padrão (DB_nK_CACHE_SIZE) O mesmo

Dois pontos importantes para a prática:

  • Com SGA_TARGET ligado, se eu definir também SHARED_POOL_SIZE, esse valor vira o tamanho mínimo da shared pool, e não um tamanho fixo.
  • No Linux, AMM e HugePages não são compatíveis. Para usar HugePages é preciso desativar o AMM. Por isso, em servidores Linux que usam HugePages, a configuração é ASMM (SGA_TARGET) e não AMM.

7. Principais processos de background

Understanding Oracle Database Memory and Process Structures

O Oracle tem dezenas de processos de background — a lista completa está na Database Reference. Abaixo estão os principais para entender a arquitetura:

Processo O que faz Pegadinha
DBWn Grava os dirty buffers nos datafiles Não grava no COMMIT
LGWR Grava o redo log buffer no online redo log Grava no COMMIT, no log switch, a cada 3 segundos, com o buffer 1/3 cheio ou com 1 MB, e antes de o DBWn gravar
CKPT Atualiza o control file e os cabeçalhos dos datafiles e sinaliza o DBWn Não grava blocos
SMON Faz o instance recovery no startup, se necessário
PMON Detecta processos que terminaram; o grupo PMON (CLMN e CLnn) faz a limpeza
LREG Registra a instância e os serviços no listener No 19c isso é do LREG, não do PMON
ARCn Arquiva o online redo log Só existe em ARCHIVELOG com arquivamento automático

O ponto central desta seção: no COMMIT, quem grava em disco é o LGWR, gravando o redo. O bloco alterado pode continuar só na memória, e o DBWn grava depois. O COMMIT não "salva a tabela": ele garante o redo em disco. É isso que permite ao Oracle ser rápido sem perder dado.

📖 Fontes: Process Architecture · Background Processes

8. Conexão × sessão; dedicated × shared server

Comparing Dedicated and Shared Server Configurations

  • Conexão: o caminho físico entre o cliente e a instância.
  • Sessão: o login lógico do usuário, que existe na memória da instância.
  • Uma conexão pode ter 0, 1 ou várias sessões.

O cliente pede a conexão ao listener, que a repassa para um handler. Depois disso, o listener sai da conversa. Quem conta ao listener quais serviços existem é o LREG, por service registration, sem precisar configurar nada no listener.ora.

👉 Dedicated server: cada cliente ganha o seu próprio server process (relação 1:1).

👉 Shared server:

  • um dispatcher recebe os pedidos de vários clientes e coloca na request queue, que fica na SGA e é comum a todos os dispatchers da instância;
  • um shared server livre executa o pedido e devolve a resposta na response queue, que é própria de cada dispatcher.

Atenção: iniciar ou parar a instância e fazer media recovery não funcionam por um dispatcher. Para isso, a conexão tem que ser dedicated.

Laboratório: para você fazer no seu 19c

Conecte como sqlplus / as sysdba (no CDB$ROOT, se o seu banco for CDB). Cada bloco tem um botão Copiar: é só colar no SQL*Plus.

Passo 1 — A instância. STATUS mostra STARTED (nomount), MOUNTED ou OPEN.

SELECT instance_name, host_name, version_full, status, startup_time
FROM   v$instance;

Passo 2 — O banco. CDB = YES em container database; CON_ID = 0 indica o CDB inteiro.

SELECT name, dbid, cdb, con_id, open_mode, log_mode
FROM   v$database;

Passo 3 — Os containers. 2 = PDB$SEED; 3 em diante = suas PDBs.

SHOW CON_NAME
SHOW PDBS

Passo 4 — Qual gerenciamento de memória? memory_target = 0 e sga_target > 0 = ASMM.

SHOW PARAMETER memory_target
SHOW PARAMETER sga_target
SHOW PARAMETER pga_aggregate

Passo 5 — A SGA em itens.

SELECT name, ROUND(bytes/1024/1024) AS mb, resizeable
FROM   v$sgainfo
ORDER  BY bytes DESC;

Passo 6 — Os processos de background e a PGA de cada um.

SELECT pname, spid, ROUND(pga_alloc_mem/1024/1024, 1) AS pga_mb
FROM   v$process
WHERE  background = 1
ORDER  BY pname;

O que observar:

  • INSTANCE_NAME (passo 1) e NAME (passo 2) são nomes de coisas diferentes.
  • No passo 6 aparecem DBW0, LGWR, CKPT, SMON, PMON, LREG… e o ARC só aparece se o banco estiver em ARCHIVELOG.

📖 Fontes: V$INSTANCE · V$DATABASE · V$SGAINFO · V$PROCESS

Pontos de atenção que encontrei nos simulados

  • Uma instância se associa a um único banco por vez; no RAC são várias instâncias para um banco.
  • Tempfile faz parte do banco, mas não aparece em V$DATAFILE: ele aparece em V$TEMPFILE.
  • O server result cache fica dentro da shared pool, não é um pool separado.
  • A large pool não tem lista LRU.
  • Dirty quer dizer "alterado e não gravado", e não "não comitado".
  • A PGA nunca fica na SGA. O que vai para a SGA em shared server é a UGA.
  • No 19c, quem registra no listener é o LREG.
  • STARTUP, SHUTDOWN e media recovery não funcionam por um dispatcher.

Resumo em 5 linhas

  1. Instância é memória (SGA) mais processos. Banco são datafiles, tempfiles, control files e online redo logs.
  2. PDBs dividem a mesma instância, mas cada uma tem SYSTEM, SYSAUX e dicionário próprios.
  3. A SGA é compartilhada; a PGA é privada e nunca fica na SGA.
  4. No COMMIT grava o LGWR (redo); o DBWn grava o bloco depois.
  5. Conexão ≠ sessão, e tarefas como STARTUP e SHUTDOWN exigem dedicated server.
