Usuários, quotas e profiles no Oracle (1Z0-082 · Parte 6)

DBACERTIFICAÇÃO

Sexta parte do Guia 1Z0-082. Na Parte 5 fechamos o bloco de gerenciar a instância. Agora começa a segurança: como nasce uma conta, onde ficam os objetos dela, quanto espaço ela pode usar e quais regras de senha e de recurso ela segue.

Achei que este assunto seria tranquilo, porque CREATE USER eu faço há anos. Só que a prova pergunta justamente o que acontece quando cada cláusula é omitida, e aí vi que eu fazia muita coisa no automático.

Cada afirmação técnica deste artigo foi conferida na documentação oficial do Oracle Database 19c. Os links estão em cada seção e reunidos no final.

1. Anatomia de um CREATE USER

Creating and Managing Users

Todo usuário tem um schema com o mesmo nome. A conta recém-criada nasce com o domínio de privilégios vazio: sem CREATE SESSION, ela nem conecta (ORA-01045). O par mínimo é sempre CREATE USER + GRANT CREATE SESSION.

O CREATE USER é uma lista de cláusulas independentes. O que vale quando cada uma é omitida:

Cláusula Se omitir
IDENTIFIED BY / EXTERNALLY / GLOBALLY / NO AUTHENTICATION Obrigatória: define como o usuário se autentica
DEFAULT TABLESPACE A default permanent tablespace do banco (ou da PDB); sem ela, SYSTEM
TEMPORARY TABLESPACE A default temporary tablespace do banco; sem ela, SYSTEM
QUOTA … ON Nenhuma quota em nenhuma tablespace
PROFILE Profile DEFAULT
PASSWORD EXPIRE A senha não expira no primeiro login
ACCOUNT LOCK / UNLOCK UNLOCK

Mais três detalhes:

  • A senha é case sensitive.
  • Sem aspas, o nome é guardado em maiúsculas (jward vira JWARD). Com aspas, fica exatamente como foi escrito, e você vai precisar das aspas para sempre.
  • Default roles não entram no CREATE USER: a conta nasce com DEFAULT ROLE ALL, e toda role concedida depois já vem ativa no login.

Para remover: DROP USER u. Se o schema tiver objetos, é preciso DROP USER u CASCADE.

2. Usuário comum × usuário local num CDB

Creating and Managing Users

Num CDB, a diferença entre os dois tipos de usuário é de alcance, não de privilégio:

Comum Local
Existe em Root e todas as PDBs (inclusive as futuras) Uma PDB
Criado conectado a CDB$ROOT A PDB
Nome Começa com C## (COMMON_USER_PREFIX) Não pode começar com C##
CONTAINER= ALL (padrão e único valor no root) CURRENT (padrão na PDB)
Exemplos SYS, SYSTEM, C##DBA APP, HR

Por isso CREATE USER app no root falha (ORA-65096), e CREATE USER c##app dentro da PDB também falha.

  • Se o CREATE USER de um usuário comum citar tablespace, quota ou profile, esses objetos precisam existir em todos os containers.
  • Um usuário comum pode ter privilégios diferentes em cada PDB.
  • Não existe conversão: comum não vira local, nem o contrário. Cria-se outra conta.

3. Default tablespace e temporary tablespace

Creating and Managing Users

  • A default tablespace recebe os objetos que o usuário cria sem dizer TABLESPACE no DDL.
  • A temporary tablespace recebe os segmentos temporários da sessão: sorts e joins que não cabem na PGA.

O que eu precisei fixar:

  • A default tablespace não pode ser temporária nem undo. A temporary precisa ser do tipo temporário.
  • Não existe quota na temporary tablespace: segmentos temporários pertencem ao SYS, e a cláusula QUOTA nem é aceita para ela.
  • Trocar a default tablespace com ALTER USER só vale para objetos novos. As tabelas antigas ficam onde estão; para movê-las, ALTER TABLE … MOVE.
  • Default tablespace não dá espaço. Sem quota, o usuário não aloca nada lá.

Para ver os padrões do banco:

SELECT property_name, property_value
FROM   database_properties
WHERE  property_name LIKE 'DEFAULT_%TABLESPACE';

📖 Fontes: Creating User Accounts · ALTER USER

4. Quotas e o ORA-01950 que aparece no INSERT

Creating and Managing Users

Quota é o limite de espaço que os segmentos de um usuário podem ocupar numa tablespace específica.

ALTER USER app QUOTA 100M ON users;       -- teto de 100 MB
ALTER USER app QUOTA UNLIMITED ON users;  -- sem teto nesta tablespace
ALTER USER app QUOTA 0 ON users;          -- retira a quota

A parte que me surpreendeu: a quota é verificada quando um extent é alocado, não quando a tabela é criada. Com a deferred segment creation (padrão desde o 11.2), um CREATE TABLE sem quota funciona, porque a tabela existe só no dicionário. O erro aparece no primeiro INSERT:

  • Sem quota: ORA-01950: no privileges on tablespace 'USERS'
  • Quota acabou: ORA-01536: space quota exceeded for tablespace

E mais:

  • Reduzir a quota não apaga nada. Com QUOTA 0, os objetos continuam lá, mas não recebem espaço novo.
  • A quota conta todos os segmentos do dono naquela tablespace (tabelas, índices, LOBs).
  • O privilégio de sistema UNLIMITED TABLESPACE ignora as quotas em todas as tablespaces. É poderoso demais para uma conta de aplicação.

5. Profiles: o conjunto de limites da conta

Creating and Managing Users

Profile é um conjunto nomeado de limites de senha e limites de recurso.

  • Cada usuário tem exatamente um profile. Atribuir outro substitui o anterior.
  • Profile se atribui só a usuários, nunca a roles.
  • Quem não recebe profile fica com o DEFAULT, que existe em todo banco e não pode ser removido.
  • Um parâmetro com valor DEFAULT quer dizer "use o valor atual do profile DEFAULT", e não "padrão de fábrica". Por isso, mudar o profile DEFAULT afeta de uma vez todo mundo que herda dele.
  • DROP PROFILE de um profile em uso exige CASCADE, e os usuários caem no DEFAULT.
  • Mudanças de profile não afetam sessões abertas: valem a partir do próximo login.
CREATE PROFILE app_prof LIMIT
  FAILED_LOGIN_ATTEMPTS 5
  PASSWORD_LOCK_TIME    1/24     -- 1 hora
  PASSWORD_LIFE_TIME    90
  SESSIONS_PER_USER     20
  IDLE_TIME             30;      -- minutos

ALTER USER app PROFILE app_prof;

6. Parâmetros de senha

Creating and Managing Users

Os valores do profile DEFAULT no 19c:

Parâmetro DEFAULT O que faz
FAILED_LOGIN_ATTEMPTS 10 Tentativas erradas seguidas até travar
PASSWORD_LOCK_TIME 1 dia Tempo travada depois disso
PASSWORD_LIFE_TIME 180 dias Validade da senha
PASSWORD_GRACE_TIME 7 dias Carência depois de vencer
PASSWORD_REUSE_TIME / PASSWORD_REUSE_MAX UNLIMITED Regras de reuso
INACTIVE_ACCOUNT_TIME UNLIMITED Trava depois de n dias sem login

Os de tempo são em dias e aceitam frações (1/24 = 1 hora).

Travamento: passou de FAILED_LOGIN_ATTEMPTS, o status vira LOCKED(TIMED) e a conta se destrava sozinha depois de PASSWORD_LOCK_TIME. Se o lock time for UNLIMITED, ou se a conta foi travada à mão com ACCOUNT LOCK, o status é LOCKED e só ALTER USER … ACCOUNT UNLOCK resolve.

Validade: vencida a senha, no próximo login o usuário entra, recebe o aviso ORA-28002 e o status vira EXPIRED(GRACE). Terminada a carência, o status é EXPIRED e o login pede a troca da senha.

Reuso: os dois parâmetros com valor, a senha só volta depois do tempo e do número de trocas. Um com valor e o outro UNLIMITED: a senha nunca pode ser reutilizada. Os dois UNLIMITED: sem restrição. Essa me pegou no simulado.

Complexidade: PASSWORD_VERIFY_FUNCTION aponta para uma função no schema SYS. O catpvf.sql cria as funções da Oracle (como ORA12C_VERIFY_FUNCTION). A verificação não se aplica ao SYS.

7. Parâmetros de recurso e o RESOURCE_LIMIT

Creating and Managing Users

Os limites de recurso: SESSIONS_PER_USER, CPU_PER_SESSION e CPU_PER_CALL (em centésimos de segundo), CONNECT_TIME e IDLE_TIME (em minutos), LOGICAL_READS_PER_SESSION e LOGICAL_READS_PER_CALL (em blocos), PRIVATE_SGA (só relevante em shared server) e COMPOSITE_LIMIT.

A pegadinha clássica:

  • RESOURCE_LIMIT liga e desliga só os limites de recurso. No 19c o padrão é TRUE e o parâmetro é dinâmico.
  • Os limites de senha valem sempre, mesmo com RESOURCE_LIMIT = FALSE.

O que acontece ao estourar:

Limite Efeito
De call (CPU_PER_CALL, LOGICAL_READS_PER_CALL) Desfaz só o comando; transação e sessão continuam
De sessão (CPU_PER_SESSION, …) Desfaz o comando; o usuário só pode dar COMMIT, ROLLBACK ou desconectar
CONNECT_TIME / IDLE_TIME Desfaz a transação e encerra a sessão
SESSIONS_PER_USER Recusa o login excedente

IDLE_TIME mede tempo sem calls: não derruba uma consulta longa que está rodando. Para governança de CPU de verdade, a Oracle recomenda o Database Resource Manager.

8. Menor privilégio, na prática

Creating and Managing Users

A recomendação da documentação é dar a cada usuário só o que ele precisa, de preferência por roles e não direto na conta. Na minha rotina, isso virou:

  • Evitar privilégios ANY (CREATE ANY PROCEDURE, DROP ANY TABLE…) em contas de aplicação.
  • Não dar UNLIMITED TABLESPACE; dar quota na tablespace certa.
  • Criar roles próprias por função em vez de usar CONNECT, RESOURCE e DBA, que existem por compatibilidade.
  • Cuidado com PUBLIC: o que é concedido a ele vale para todo usuário, inclusive os que ainda vão ser criados.

📖 Fontes: Guidelines for Securing User Accounts and Privileges

Laboratório: para você fazer no seu 19c

Conecte como SYSDBA e entre numa PDB de teste (ALTER SESSION SET CONTAINER = orclpdb1;). Troque orclpdb1 pelo nome da sua PDB. Só em laboratório. Cada bloco tem um botão Copiar.

Passo 1 — O retrato do banco e do profile DEFAULT.

SELECT property_name, property_value FROM database_properties
 WHERE property_name LIKE 'DEFAULT_%TABLESPACE';
SHOW PARAMETER resource_limit
SELECT resource_name, resource_type, limit FROM dba_profiles
 WHERE profile = 'DEFAULT' ORDER BY resource_type, resource_name;

Passo 2 — Criar o usuário sem quota. O SQL*Plus pede a senha sem mostrar na tela.

ACCEPT senha CHAR PROMPT 'Senha para LAB06: ' HIDE
CREATE USER lab06 IDENTIFIED BY "&senha"
  DEFAULT TABLESPACE users TEMPORARY TABLESPACE temp;
SELECT username, account_status, default_tablespace, profile, common
  FROM dba_users WHERE username = 'LAB06';

Tente conectar como lab06 em outro terminal: ORA-01045.

Passo 3 — CREATE TABLE funciona, INSERT falha.

GRANT CREATE SESSION, CREATE TABLE TO lab06;
-- conectado como lab06:
CREATE TABLE t (id NUMBER);
INSERT INTO t VALUES (1);   -- ORA-01950

Passo 4 — Dar quota e tentar de novo.

ALTER USER lab06 QUOTA 5M ON users;
-- como lab06:
INSERT INTO t VALUES (1);
COMMIT;

Passo 5 — Profile que trava rápido.

CREATE PROFILE lab_prof LIMIT FAILED_LOGIN_ATTEMPTS 3 PASSWORD_LOCK_TIME 1/1440;
ALTER USER lab06 PROFILE lab_prof;

Erre a senha de lab06 três vezes e confira:

SELECT username, account_status, lock_date, profile
  FROM dba_users WHERE username = 'LAB06';

O status deve aparecer como LOCKED(TIMED). Espere um minuto ou destrave com ALTER USER lab06 ACCOUNT UNLOCK;.

Passo 6 — Limpeza.

DROP USER lab06 CASCADE;
DROP PROFILE lab_prof;

Pontos de atenção que encontrei nos simulados

  • Usuário novo não conecta sem CREATE SESSION (ORA-01045).
  • Sem DEFAULT TABLESPACE, vale a do banco; sem ela, SYSTEM.
  • Default tablespace não dá quota. Sem quota, o erro aparece no primeiro INSERT (ORA-01950), não no CREATE TABLE.
  • Não existe quota na temporary tablespace.
  • QUOTA 0 não apaga objetos.
  • Usuário comum: C##, criado no root, CONTAINER=ALL. Local: na PDB, sem C##.
  • Profile se atribui só a usuários; o DEFAULT não pode ser removido.
  • DEFAULT num parâmetro = valor atual do profile DEFAULT.
  • DROP PROFILE em uso exige CASCADE; os usuários vão para o DEFAULT.
  • Padrões: 10 tentativas, 1 dia travada, 180 dias de validade, 7 de carência.
  • LOCKED(TIMED) destrava sozinha; LOCKED só com ACCOUNT UNLOCK.
  • Reuso: um com valor e o outro UNLIMITED = nunca reutiliza.
  • RESOURCE_LIMIT = FALSE não desliga os limites de senha.
  • CPU em centésimos de segundo; IDLE_TIME e CONNECT_TIME em minutos.

Resumo em 5 linhas

  1. CREATE USER + CREATE SESSION é o mínimo; cada cláusula omitida tem um padrão que cai na prova.
  2. Num CDB, comum (C##, no root, em todas as PDBs) × local (só numa PDB).
  3. Default tablespace diz onde; quota diz quanto. Sem quota, o erro só aparece no INSERT.
  4. Profile = limites de senha (sempre ativos) + limites de recurso (dependem do RESOURCE_LIMIT).
  5. Menor privilégio: roles próprias, quota em vez de UNLIMITED TABLESPACE, nada de ANY para aplicação.
