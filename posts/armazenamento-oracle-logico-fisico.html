Segunda parte do Guia 1Z0-082. Na Parte 1 vimos a instância: memória e processos. Agora o foco é onde e como os dados ficam guardados: as estruturas lógicas que o Oracle gerencia, os arquivos físicos que o sistema operacional enxerga e o caminho que um UPDATE percorre até virar dado seguro em disco.

1. Lógico × físico: a tablespace é a ponte

Understanding Logical and Physical Database Structures

O Oracle organiza o armazenamento em dois mundos:

👉 Lógico (o que o banco gerencia): tablespace → segmento → extent → data block.

👉 Físico (o que o sistema operacional enxerga): datafiles e tempfiles, control files e online redo log files, todos formados por blocos do SO.

A ligação entre os dois acontece em dois pontos:

  • No topo: a tablespace é formada por um ou mais datafiles (ou tempfiles, se for temporária).
  • Na base: cada data block corresponde a um número inteiro de blocos do SO.

Duas regras de fronteira resolvem muita dúvida:

  • Um extent está sempre dentro de um único datafile. Nunca atravessa arquivos.
  • Um segmento pertence a uma única tablespace, mas pode ter extents em datafiles diferentes dessa tablespace.
Estrutura É feita de Limite
Tablespace Segmentos (lógico) / datafiles ou tempfiles (físico) Um datafile pertence a uma só tablespace
Segmento Extents de um objeto (ou partição) Nunca atravessa tablespaces
Extent Data blocks logicamente contíguos Sempre dentro de um único datafile
Data block Blocos do SO Menor unidade de I/O do Oracle

2. O data block por dentro

Understanding Block Space Management

O data block é a menor unidade de armazenamento: o Oracle lê e grava em múltiplos de blocos.

  • O tamanho padrão é o DB_BLOCK_SIZE, definido na criação do banco.
  • Mínimo de 2 KB, máximo de 32 KB, e sempre múltiplo do bloco físico do SO.

Por dentro, o bloco tem:

  • Block overhead: cabeçalho, table directory e row directory, em média 84 a 107 bytes. O espaço do row directory não é devolvido quando linhas são apagadas; ele só é reaproveitado por novos INSERTs no bloco.
  • ITL (interested transaction list): fica no cabeçalho e indica quais transações têm linhas travadas no bloco. O Oracle guarda a informação de lock no próprio bloco, e não numa lista de locks em memória.
  • Row data e free space: as linhas e o espaço livre entre elas e o cabeçalho.

O PCTFREE reserva uma porcentagem do bloco para os UPDATEs das linhas que já existem. O padrão é 10: os INSERTs enchem o bloco até 90%.

Row migration Row chaining
Causa Um UPDATE faz a linha crescer e ela não cabe mais no bloco A linha é grande demais para um bloco já no INSERT
O que acontece A linha vai inteira para outro bloco A linha fica em pedaços encadeados

3. Extents, segmentos e deferred segment creation

Deferring Segment Creation

Extent é um conjunto de blocos contíguos alocados de uma vez. Nas tablespaces locally managed (o padrão), o tamanho segue uma de duas políticas:

  • AUTOALLOCATE (padrão): o Oracle escolhe o tamanho, com extent mínimo de 64 KB.
  • UNIFORM: todos do mesmo tamanho; 1 MB se você não informar.

Segmento é o conjunto de extents de um objeto: tabela, partição, índice, LOB, undo ou temporário. Views, sequences e synonyms não têm segmento: são só metadados.

Deferred segment creation: no 19c, DEFERRED_SEGMENT_CREATION = TRUE é o padrão. O CREATE TABLE grava só metadados. Os segmentos da tabela, dos índices e dos LOBs nascem no primeiro INSERT.

High water mark (HWM): separa os blocos que já foram usados dos que nunca foram. Ela só recua com rebuild, TRUNCATE ou SHRINK. Um DELETE, mesmo de todas as linhas, não devolve o espaço para a tablespace.

Smallfile × bigfile:

  • Smallfile (tradicional): até 1023 datafiles, cada um com até cerca de 4 milhões (2²²) de blocos.
  • Bigfile: um único datafile, com até cerca de 4 bilhões (2³²) de blocos. São 32 TB com bloco de 8 KB e 128 TB com 32 KB.

Tablespace read only: dá para remover objetos (DROP TABLE funciona), mas não dá para criar nem alterar.

5. Datafiles, tempfiles e control files

Understanding Logical and Physical Database Structures

Datafiles guardam os dados de tabelas, índices, undo e dicionário. Cada um pertence a uma única tablespace.

Tempfiles pertencem às tablespaces temporárias e se comportam diferente:

  • nunca guardam objetos permanentes;
  • o media recovery não os reconhece;
  • aparecem em V$TEMPFILE e DBA_TEMP_FILES, e não em V$DATAFILE nem em DBA_DATA_FILES.

Control file: um arquivo binário pequeno que registra a estrutura física do banco:

  • nome do banco e data de criação;
  • nomes e locais dos datafiles e dos redo logs;
  • número de sequência do log corrente;
  • informação de checkpoint.

É lido no estágio MOUNT.

A multiplexação dos control files funciona assim:

  • A instância grava em todas as cópias listadas em CONTROL_FILES, mas lê só a primeira.
  • Se uma cópia fica indisponível com o banco aberto, a instância fica inoperante. Multiplexar não evita a queda; evita a perda.
  • Com uma cópia boa, basta restaurá-la por cima da danificada e reiniciar, sem media recovery.

📖 Fontes: Physical Storage Structures · Managing Control Files

6. Online redo log: grupos, membros e log switch

Understanding Logical and Physical Database Structures

O online redo log registra todas as mudanças para que possam ser refeitas numa recuperação.

  • São no mínimo dois grupos, e cada arquivo tem no mínimo 4 MB.
  • Cada grupo pode ter vários membros, que são cópias idênticas. O LGWR grava em todos os membros do grupo corrente ao mesmo tempo.
  • Se um membro falha, ele fica marcado como INVALID e o LGWR segue gravando nos outros. Se todos os membros do próximo grupo estão inacessíveis no log switch, a instância cai.

O uso é circular: quando o grupo corrente enche, acontece o log switch e o LGWR passa para o próximo grupo.

Estados em V$LOG:

  • CURRENT: o grupo em que o LGWR está gravando.
  • ACTIVE: ainda necessário para o instance recovery.
  • INACTIVE: não é mais necessário para o instance recovery.

Só se remove um grupo inativo e, em ARCHIVELOG, depois de arquivado.

NOARCHIVELOG ARCHIVELOG
Grupo pode ser reutilizado quando As mudanças nele foram gravadas nos datafiles Isso e o grupo foi arquivado

7. Arquivos que não são o banco

Using the Alert Log and Trace Files

O banco é composto por datafiles, tempfiles, control files e online redo logs. Outros arquivos são indispensáveis para operar o servidor, mas não fazem parte do banco:

Arquivo Para quê
spfile / pfile Parâmetros de inicialização da instância (lidos no NOMOUNT)
Password file Autenticar SYSDBA, SYSOPER e afins com o banco fechado ou remotamente
Alert log e trace files Diagnóstico. Ficam no ADR (Automatic Diagnostic Repository), fora do banco
Archived redo logs e backups Recuperação

Um detalhe útil: o alert log é criado quando a instância sobe pela primeira vez, mesmo antes de existir banco. V$DIAG_INFO mostra onde ele está.

8. Arquitetura em ação: UPDATE, COMMIT e instance recovery

Understanding Oracle Database Server Architecture

Juntando a Parte 1 com esta, um UPDATE seguido de COMMIT fica assim:

  1. O server process faz o parse: soft parse se o SQL já está na library cache, hard parse se não está.
  2. Lê o bloco para o buffer cache, grava os valores antigos no undo, trava a linha (ITL) e altera o bloco.
  3. As mudanças no bloco de dados e no bloco de undo geram redo, que vai para o redo log buffer.
  4. No COMMIT, o LGWR grava o redo no online redo log, e só então o COMMIT retorna.
  5. Mais tarde, o DBWn grava os blocos alterados nos datafiles, sempre depois do redo correspondente.

Enquanto isso, as consultas veem os dados confirmados no momento em que começaram (statement-level read consistency): leitores não bloqueiam escritores, e escritores não bloqueiam leitores. Se o undo necessário já foi sobrescrito, uma consulta longa pode falhar com snapshot too old.

Se a instância cair, o SMON faz o instance recovery sozinho no próximo STARTUP:

  • Roll forward (cache recovery): reaplica tudo o que está no online redo. Como o redo também protege o undo, os segmentos de undo são regenerados.
  • Roll back (transaction recovery): usa o undo para desfazer o que não foi confirmado. Novas transações não precisam esperar o SMON terminar: elas mesmas desfazem os blocos de que precisam.

9. Schemas e schema objects

Understanding Logical and Physical Database Structures

Schema é a coleção de objetos de um usuário, com o mesmo nome dele: o usuário HR tem o schema HR.

O ponto que mais confunde: schema e tablespace não têm relação. Uma tablespace pode guardar objetos de vários schemas, e os objetos de um schema podem estar em várias tablespaces.

Objeto Tem segmento?
Tabela, índice, LOB, partição Sim
View, sequence, synonym Não (só metadados)
Procedure / package Não (código no dicionário)

Laboratório: para você fazer no seu 19c

Conecte como sqlplus / as sysdba. Os passos 1 a 3 rodam no CDB$ROOT; do passo 4 em diante, entre na sua PDB. Cada bloco tem um botão Copiar.

Passo 1 — Control files. Mais de uma linha = multiplexado.

SELECT name FROM v$controlfile;
SHOW PARAMETER control_files

Passo 2 — Grupos e membros do online redo log. Exatamente um grupo fica CURRENT.

SELECT group#, sequence#, ROUND(bytes/1024/1024) AS mb, members, archived, status
FROM   v$log
ORDER  BY group#;

SELECT group#, status, member
FROM   v$logfile
ORDER  BY group#;

Passo 3 — Modo de arquivamento.

ARCHIVE LOG LIST
SELECT log_mode FROM v$database;

Passo 4 — Tablespaces da PDB. Troque orclpdb1 pelo nome da sua PDB.

ALTER SESSION SET CONTAINER = orclpdb1;

SELECT tablespace_name, contents, bigfile, block_size,
       extent_management, allocation_type, segment_space_management
FROM   dba_tablespaces
ORDER  BY 1;

Passo 5 — Datafiles × tempfiles. Repare que o tempfile só aparece na segunda consulta.

SELECT file_id, tablespace_name, ROUND(bytes/1024/1024) AS mb, file_name
FROM   dba_data_files
ORDER  BY file_id;

SELECT file_id, tablespace_name, ROUND(bytes/1024/1024) AS mb, file_name
FROM   dba_temp_files;

Passo 6 — Deferred segment creation na prática. O segmento só aparece depois do primeiro INSERT.

CREATE TABLE lab_seg (id NUMBER);

SELECT segment_created FROM user_tables WHERE table_name = 'LAB_SEG';
SELECT COUNT(*) FROM user_segments WHERE segment_name = 'LAB_SEG';

INSERT INTO lab_seg VALUES (1);
COMMIT;

SELECT COUNT(*) FROM user_segments WHERE segment_name = 'LAB_SEG';

DROP TABLE lab_seg PURGE;

Faça o passo 6 com um usuário comum da PDB cuja tablespace padrão não seja a SYSTEM. A criação adiada não vale para tabelas de SYS, SYSTEM, PUBLIC, OUTLN e XDB, nem na tablespace SYSTEM.

Pontos de atenção que encontrei nos simulados

  • Extent nunca atravessa datafiles; segmento nunca atravessa tablespaces.
  • PCTFREE reserva espaço para UPDATE de linhas existentes, não para INSERT. Padrão: 10.
  • Row migration mantém o rowid.
  • No 19c, CREATE TABLE não cria segmento por padrão: ele nasce no primeiro INSERT.
  • DELETE não baixa a high water mark; TRUNCATE sim.
  • SYSTEM, undo e temporárias não ficam offline.
  • Em tablespace read only dá para fazer DROP, mas não CREATE nem ALTER.
  • Bigfile = um único datafile.
  • A instância grava em todas as cópias do control file, mas lê só a primeira.
  • Tempfile não aparece em V$DATAFILE.
  • Só se remove grupo de redo inativo.
  • Instance recovery: primeiro roll forward (redo), depois roll back (undo).
  • Schema não tem relação com tablespace.

Resumo em 5 linhas

  1. Lógico: tablespace → segmento → extent → bloco. Físico: datafiles, tempfiles, control files e online redo logs.
  2. Extent fica em um datafile só; segmento fica em uma tablespace só.
  3. O control file é o mapa físico do banco, lido no MOUNT; multiplexar evita perder o arquivo, não a queda.
  4. O online redo é circular, com no mínimo dois grupos; em ARCHIVELOG cada grupo é arquivado antes de ser reutilizado.
  5. Depois de uma queda, o SMON faz roll forward com o redo e roll back com o undo.
