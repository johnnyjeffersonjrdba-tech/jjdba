PFILE, SPFILE e o SCOPE do ALTER SYSTEM (1Z0-082 · Parte 5)

DBACERTIFICAÇÃO

Quinta parte do Guia 1Z0-082. Na Parte 4 vimos onde o DBA busca informação: dicionário, V$ e ADR. Agora o assunto é o arquivo que a instância lê antes de tudo: os arquivos de parâmetros. Spfile × pfile, a ordem em que o STARTUP procura cada um, o SCOPE do ALTER SYSTEM e como sair de um parâmetro errado sem pânico.

Confesso que este foi o dia em que entendi por que, no passado, eu mudava um parâmetro e ele "sumia" depois do restart.

Cada afirmação técnica deste artigo foi conferida na documentação oficial do Oracle Database 19c. Os links estão em cada seção e reunidos no final.

1. Por que existe um arquivo de parâmetros

Managing Initialization Parameter Files

Lembra do estágio NOMOUNT da Parte 3? A primeira coisa que a instância faz é ler os parâmetros de inicialização. É com eles que ela sabe o tamanho da SGA, onde estão os control files (CONTROL_FILES), o nome do banco (DB_NAME), o DIAGNOSTIC_DEST e tudo mais. Sem esse arquivo, a instância nem chega a nascer.

Esse arquivo pode ter dois formatos:

PFILE (text initialization parameter file) SPFILE (server parameter file)
Formato Texto Binário
Quem edita Você, num editor de texto O próprio Oracle, via ALTER SYSTEM
Mudança com ALTER SYSTEM sobrevive ao restart? Não Sim (com SCOPE=SPFILE ou BOTH)
Nome padrão init<SID>.ora spfile<SID>.ora
Recomendado pela Oracle — Sim

O spfile não pode ser editado num editor de texto. Abrir no vi e salvar é um jeito clássico de corromper o arquivo. Para mudar, use ALTER SYSTEM; para ler, use V$SPPARAMETER ou gere um pfile a partir dele.

No Linux, os dois ficam por padrão em $ORACLE_HOME/dbs.

2. A ordem de busca no STARTUP

Managing Initialization Parameter Files

Quando você dá STARTUP sem informar arquivo, a instância procura, nesta ordem:

  1. spfile<SID>.ora
  2. spfile.ora
  3. init<SID>.ora

Para no primeiro que encontrar. Ou seja: se existe um spfile, o pfile do mesmo diretório é ignorado, mesmo que você tenha acabado de editá-lo. Essa me pegou.

Para subir com um pfile específico:

STARTUP PFILE='/u01/app/oracle/dbs/initteste.ora'

O comando STARTUP do SQL*Plus aceita PFILE=, mas não tem uma opção SPFILE=. Para usar um spfile fora do lugar padrão, o caminho é um pfile com uma única linha, SPFILE='/caminho/spfileXYZ.ora', e subir com ele.

Para saber com qual arquivo a instância subiu:

SHOW PARAMETER spfile

Valor vazio = a instância subiu com pfile.

3. ALTER SYSTEM e o SCOPE

Managing Initialization Parameter Files

Esta é a parte que mais cai. O SCOPE diz onde a mudança vale:

SCOPE Vale agora? Vale depois do restart?
MEMORY Sim Não
SPFILE Não Sim
BOTH Sim Sim

E o que eu precisei decorar:

  • Sem SCOPE, o padrão é BOTH se a instância subiu com spfile, e MEMORY se subiu com pfile.
  • Se a instância subiu com pfile, SCOPE=SPFILE e SCOPE=BOTH dão erro: não há spfile para gravar.
  • Parâmetro estático não muda em memória: só aceita SCOPE=SPFILE, e a mudança vale no próximo startup.
  • Com SCOPE=SPFILE ou BOTH, dá para gravar um comentário junto: COMMENT='motivo da mudança'. Recomendo fazer isso sempre.
ALTER SYSTEM SET open_cursors = 500 SCOPE=BOTH COMMENT='chamado 1234';
ALTER SYSTEM SET processes   = 600 SCOPE=SPFILE;   -- estático: vale no próximo startup

📖 Fontes: ALTER SYSTEM · Managing Initialization Parameters Using a Server Parameter File

4. Estático, dinâmico e DEFERRED: como saber

Managing Initialization Parameter Files

Não precisa decorar parâmetro por parâmetro. A V$PARAMETER responde:

Coluna O que diz
ISSES_MODIFIABLE TRUE: pode mudar só na sua sessão com ALTER SESSION
ISSYS_MODIFIABLE IMMEDIATE: muda já · DEFERRED: só para sessões novas · FALSE: estático
ISPDB_MODIFIABLE TRUE: pode ter valor próprio em cada PDB
ISDEFAULT / ISMODIFIED Se está no valor padrão e se foi alterado depois do startup

Quando ISSYS_MODIFIABLE = DEFERRED, a palavra DEFERRED é obrigatória no ALTER SYSTEM: o novo valor vale para as sessões que conectarem depois, e as atuais ficam com o antigo.

E as três views que confundem:

  • V$PARAMETER: valores em vigor na sua sessão.
  • V$SYSTEM_PARAMETER: valores em vigor na instância.
  • V$SPPARAMETER: o que está gravado no spfile (se a instância subiu com pfile, a coluna ISSPECIFIED vem toda FALSE).

📖 Fontes: V$PARAMETER · V$SYSTEM_PARAMETER · V$SPPARAMETER · ALTER SYSTEM

5. CREATE PFILE, CREATE SPFILE e FROM MEMORY

Managing Initialization Parameter Files

Os comandos para ir de um formato ao outro:

CREATE PFILE FROM SPFILE;                         -- cópia legível do spfile
CREATE SPFILE FROM PFILE;                         -- (re)cria o spfile a partir do texto
CREATE PFILE='/tmp/init_agora.ora' FROM MEMORY;   -- foto dos valores em uso
CREATE SPFILE FROM MEMORY;                        -- recria o spfile com o que está em memória
  • Exigem SYSDBA, SYSOPER, SYSBACKUP ou SYSDG. Num CDB, só no root.
  • Funcionam até com a instância parada (menos o FROM MEMORY, que precisa dela no ar).
  • Sem caminho, usam o nome e o diretório padrão.
  • Não dá para sobrescrever o spfile que a instância está usando com CREATE SPFILE FROM PFILE: gere com outro nome ou faça com a instância parada.

O FROM MEMORY é o salva-vidas de quando o spfile se perde com o banco no ar.

📖 Fontes: CREATE PFILE · CREATE SPFILE

6. Desfazendo: ALTER SYSTEM RESET

Managing Initialization Parameter Files

Para tirar um parâmetro do spfile e voltar ao padrão, use RESET, e não SET com o valor que você "acha" que é o padrão:

ALTER SYSTEM RESET open_cursors SCOPE=SPFILE;

Com SCOPE=SPFILE, o parâmetro sai do spfile e o padrão vale a partir do próximo startup.

Num CDB: quando um parâmetro com ISPDB_MODIFIABLE = TRUE é alterado dentro de uma PDB, o valor fica guardado na própria PDB, e não no spfile do CDB. Um RESET dentro da PDB faz ela voltar a herdar o valor do root.

📖 Fontes: ALTER SYSTEM · Managing Initialization Parameters Using a Server Parameter File

7. O caso real: o banco não sobe por causa de um parâmetro

Esse é o cenário que justifica tudo acima. Alguém faz ALTER SYSTEM SET ... SCOPE=SPFILE com um valor inválido, e no próximo restart a instância não passa do NOMOUNT. Como o spfile é binário, não dá para "abrir e corrigir". O roteiro:

  1. CREATE PFILE='/tmp/conserto.ora' FROM SPFILE; (funciona com a instância parada)
  2. Corrigir a linha no /tmp/conserto.ora com um editor.
  3. STARTUP PFILE='/tmp/conserto.ora'
  4. Com o banco no ar, CREATE SPFILE FROM PFILE='/tmp/conserto.ora'; e, num próximo restart, voltar a usar o spfile.

Por isso mesmo, antes de qualquer mudança com SCOPE=SPFILE, eu faço um CREATE PFILE='/backup/init_antes.ora' FROM SPFILE;. Custa um segundo.

Laboratório: para você fazer no seu 19c

Conecte como sqlplus / as sysdba no CDB$ROOT. Use um ambiente de teste. Cada bloco tem um botão Copiar.

Passo 1 — Com qual arquivo a instância subiu?

SHOW PARAMETER spfile

Passo 2 — Estático ou dinâmico?

SELECT name, isses_modifiable, issys_modifiable, ispdb_modifiable, isdefault
FROM   v$parameter
WHERE  name IN ('processes', 'open_cursors', 'sort_area_size', 'sga_target');

Passo 3 — Os três SCOPEs. Compare a memória e o spfile depois de cada comando.

ALTER SYSTEM SET open_cursors = 400 SCOPE=MEMORY;
ALTER SYSTEM SET open_cursors = 450 SCOPE=SPFILE COMMENT='lab parte 5';
SELECT value FROM v$system_parameter WHERE name = 'open_cursors';
SELECT value, update_comment FROM v$spparameter WHERE name = 'open_cursors';

Passo 4 — O erro do parâmetro estático. Tente mudar em memória e veja o erro.

ALTER SYSTEM SET processes = 400 SCOPE=MEMORY;

Passo 5 — Cópias de segurança.

CREATE PFILE='/tmp/init_lab.ora' FROM SPFILE;
CREATE PFILE='/tmp/init_mem.ora' FROM MEMORY;

Passo 6 — Ler e comparar no shell.

grep -i open_cursors /tmp/init_lab.ora /tmp/init_mem.ora

Passo 7 — Desfazer.

ALTER SYSTEM RESET open_cursors SCOPE=SPFILE;
ALTER SYSTEM SET open_cursors = 300 SCOPE=MEMORY;   -- ou o valor que estava no passo 2

Pontos de atenção que encontrei nos simulados

  • Ordem de busca: spfile<SID>.ora → spfile.ora → init<SID>.ora. Existindo spfile, o pfile é ignorado.
  • Spfile é binário: não se edita com editor de texto.
  • SHOW PARAMETER spfile vazio = instância subiu com pfile.
  • Sem SCOPE: BOTH com spfile, MEMORY com pfile.
  • Subiu com pfile: SCOPE=SPFILE e SCOPE=BOTH falham.
  • Parâmetro estático: só SCOPE=SPFILE + restart.
  • ISSYS_MODIFIABLE = DEFERRED exige a palavra DEFERRED; vale para sessões novas.
  • V$PARAMETER = sessão · V$SYSTEM_PARAMETER = instância · V$SPPARAMETER = conteúdo do spfile.
  • CREATE PFILE/SPFILE exige SYSDBA/SYSOPER/SYSBACKUP/SYSDG e funciona com a instância parada (exceto FROM MEMORY).
  • STARTUP aceita PFILE=, mas não SPFILE=.

Resumo em 5 linhas

  1. A instância lê os parâmetros no NOMOUNT: spfile (binário, recomendado) ou pfile (texto).
  2. A busca é spfile<SID> → spfile → init<SID>, e para no primeiro que encontrar.
  3. SCOPE: MEMORY (agora), SPFILE (próximo startup), BOTH (os dois); estático só aceita SPFILE.
  4. A V$PARAMETER diz se o parâmetro é de sessão, imediato, deferred ou estático.
  5. CREATE PFILE FROM SPFILE antes de mexer, e RESET para voltar ao padrão.
